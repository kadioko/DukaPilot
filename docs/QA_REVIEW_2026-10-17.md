# System QA review - 2026-10-17

Reviewed repository HEAD `05ab9c5` and the local fixes described below. This was an audit of source, automated browser flows, database integrity, the Android wrapper, and printer bridge. Production checks were limited to unauthenticated availability requests. No real merchant records or money were changed during this audit.

## Confirmed bugs fixed locally

1. **Livestock event retry scope:** a replay looked up a group/request pair before checking its shop. An actor with another group's ID and retry key could receive that group's event and animal count. Both the normal replay and uniqueness-conflict recovery now filter through the authenticated shop. Covered in `backend/tests/farm.unit.test.js`.
2. **Receipt retries without a date:** the request hash included a new server timestamp on every attempt. An unchanged retry could receive a false conflict after the first save. Omitted dates now have a stable fingerprint; older receipts can still be replayed using their saved date. Changed details still receive a conflict. Covered in `backend/tests/stockReceipt.unit.test.js`.
3. **Sale void versus shift close:** voiding read the shift's status before acquiring its lock. A concurrent close could finish first and still be followed by a void that changed its cash history. The check now uses the status returned by the locked row. Reproduced against PostgreSQL before the fix; the regression now passes.
4. **Sale void versus debt collection:** cancellation could overwrite a debt after a concurrent collection. Cancelling the linked debt now requires zero collected amount and no payment rows in the guarded update. A conflict rolls back the sale/stock changes. Reproduced against PostgreSQL before the fix; the regression now passes.
5. **Expense custom dates and comparison period:** date-only ranges started at UTC noon and ended at UTC day-end, while sales figures used the default period. Dates now cover complete Tanzania business days and the sales comparison uses the same selected boundaries. Covered in `backend/tests/expense.unit.test.js`.
6. **Expense profit pressure after customer returns:** the overview used original completed sales without subtracting dated returns. It now subtracts returned revenue and reverses cost only for sellable/restocked units; damaged units remain a cost. Unit and PostgreSQL checks cover the formula.
7. **Expense method correction to cash:** changing an unassigned non-cash expense to cash did not attach it to an available open drawer. It now uses the actor's current open shift, following normal cash-expense treatment and preserving the existing closed-shift guard. Covered in `backend/tests/expense.unit.test.js`.

The new `backend/tests/salesIntegrity.postgres.test.js` is included in `npm run test:postgres-integrity`. It also exercises simultaneous customer-return retries, the cumulative return limit, integer refund rounding, sellable versus damaged stock, and Daily Close totals.

Two existing browser checks, `farm-eggs.spec.ts` and `staff.permissions.spec.ts`, were passing when run directly but absent from `test:mocked`. Both are now included in the regular CI command.

## Remaining findings

### High: crop-cycle results after damaged customer returns

The customer return is correctly recorded in Sales, main Analytics, and the cash/payment totals. However, crop allocations are restored only for sellable units. A fully damaged return skips that operation, leaving the crop batch's realized revenue/profit unchanged.

This was reproduced using the real return controller and a synthetic local PostgreSQL fixture:

- Harvest: two units, total cost TZS 1,000.
- Sale: TZS 2,000; original profit TZS 1,000.
- Return: one damaged unit; TZS 1,000 refunded; no stock restored.
- Correct net crop revenue/profit: TZS 1,000 / TZS 0.
- Observed crop-cycle revenue/profit: TZS 2,000 / TZS 1,000.

Trace: `backend/src/controllers/saleReturn.controller.js` skips crop restoration when restock quantity is zero; `backend/src/lib/cropHarvestSales.js` changes only sellable allocations; `backend/src/controllers/crop.controller.js` reports the saved realized totals.

At the time of the original audit, this remained unfixed. A durable return-to-harvest allocation ledger was needed to reverse revenue for every returned unit, restore cost only for sellable units, retain damaged costs, and handle mixed lots and historical returns without inventing allocations.

### Customer-return corrections remain a missing workflow

At the time of the original audit, there was no linked reversal/correction action for a mistaken customer return. Normal returns and retries worked, but an incorrectly recorded return required support reconciliation.

### Android maintenance warnings

The wrapper passes release lint and a debug build with zero lint errors and 19 warnings. The warnings cover legacy shortcut attributes, backup extraction rules, unused resources, and launcher icon metadata. These do not fail the build, but the backup/icon warnings deserve a focused Android maintenance pass and device QA.

## Follow-up: crop returns and customer-return corrections

The two findings above were subsequently fixed in the local worktree:

- Customer returns now append per-harvest return allocations. Both damaged and sellable quantities reduce crop-cycle sold quantity and realized revenue; only sellable quantities restore remaining crop stock and cost. Migration `20261017001000_customer_return_reversals_crop_allocations` backfills eligible historical damaged returns against existing FIFO allocations.
- Sales history now offers **Correct return** to owners and staff with Reports permission. It creates a linked full reversal without editing/deleting the original return, restores debt reduction without deleting payments, and records linked stock/farm/crop adjustments. A correction is rejected when returned stock is no longer available to remove. Partial correction is intentionally not supported.
- If the original return recorded a refund, the operator must attest that the money was actually recovered and record its method. Cash recovery requires an open shift and appears as a separately dated inflow in that shift's Daily Close; the original refund remains in the original shift. DukaPilot does not initiate or independently verify the external money movement.
